# Changelog of the libretro core

What changed in the libretro core of this fork, newest first. Changes that come with a merge of upstream shadPS4 are in upstream's own history; a merge is noted here with the upstream commit it brought in.

## Unreleased

- libretro-common resynced with RetroArch (d5eedad): the VFS (vfs_implementation.c, vfs.h) and the memory and interface streams had moved on; on Windows a file is now read and written at offsets on its handle (positional I/O), and read-only files get a handle of their own. Every file the core has is identical to RetroArch's again. RetroArch's VFS sample tests pass on Linux, and their positional, bulk-read, seek, large-file, overflow, descriptor and close tests built for Windows pass under wine. Built on Linux and Windows.
- A seek in FLAC music goes through the file's seek table where it has one: input resumes at the seek point nearest before the frame, at that point's own frame, and is decoded on from there, instead of from the start (back) or from where the track was (far forward); a seek back no longer makes the decoder again (an allocation) unless the file has no table. rflac could not do this, since its seek gave the byte a point is at but not the frame; the RetroArch change that adds rflac_seek_point (and with it fixes audio_transfer's FLAC seeks, which landed past their target) is in, and libretro-common's rflac.c and rflac.h are synced with it, identical to RetroArch's. Tested in libretro/tests/audio_stream_test.c on a 24-bit FLAC with a seek table made by flac and metaflac (seeks forward and back land on the frame); not heard in a game.
- Music in an MP4 or M4A file is decoded a block at a time too, to float, like the other formats since the last change: the track's AAC packets are taken from the file by rmp4 as they are needed and decoded by raac, with the encoder's delay the edit list gives trimmed as rmp4_audio does (the same samples as rmp4_audio's whole decode, which it replaces: tested; rmp4_audio.c is no longer built into the core). An M4A no longer takes its whole length decoded in memory, at 16 bits. A seek forward in an MP3 or a FLAC now decodes on from where the track is instead of from its start, so only a seek back makes a FLAC decoder again (an allocation). An AAC seek (ADTS or MP4) is primed with two access units instead of one: with HE-AAC (SBR, such as a 22.05 kHz track) one left the samples after the seek off from the ones a play from the start has. Tested in libretro/tests/audio_stream_test.c (MP4 against rmp4_audio's decode, seeks forward and back, HE-AAC in ADTS and MP4); not heard in a game.
- Music (the music player) is decoded a block at a time as it plays, straight to float, instead of a whole track to 16 bits before a note of it was heard: a track no longer takes its whole length decoded in memory (a five-minute track was 50 MiB), starts without waiting for the whole decode, and reaches the mix without being rounded to 16 bits first (a 24-bit FLAC keeps its 24 bits, MP3 and AAC their decoders' float output). The decoders are libretro-common's (rmp3, rflac, raac) in a new C89 file, src/common/audio_stream.c, which replaces audio_file.cpp; the resampler reads a window of the track in place (8192 frames, made with the player, so playing allocates nothing for it), decoded on into only when nothing more can be written from it (audio_mix_resample_ready). Seeking lands on the frame asked for (an MP3 and a FLAC are decoded forward from the start to it, as rmp3 did already; an AAC is primed with one access unit before it). An MP4/M4A is still decoded whole when it starts, to 16 bits, since rmp4_audio has no block decode. Also fixed in the resampler, for every source it reads: a position just short of a whole frame (its fraction from 0xffffff80 up) came out as a fraction of 1.0 and read a row past the end of the sinc table. Tested: libretro/tests/audio_stream_test.c on a sine made by ffmpeg in each format (the length, blocks of any size giving the same samples, seeks, samples off the 16-bit grid) and libretro/tests/audio_mix_test.c (the window gives the same output, sample for sample, as resampling a whole source, at five rates); not heard in a game.
- An HDR game is told how bright the display goes. sceSystemServiceGetHdrToneMapLuminance, which a game asks for the peak and black level to tone map its picture to, was a stub that wrote nothing: the game read whatever its memory held, so its HDR could be graded for any peak at all. It now gives the frontend's target peak and black level (GET_HDR_METADATA's max_nits and min_nits, with HDR Output on; 1000 and 0.01 nits otherwise or when the frontend gives none), in the struct's layout as fpPS4 has it (full-frame peak, peak, black, three floats); the full-frame peak is the peak, the frontend not saying what a display holds over the whole screen. Also put right: the last change's libretro_core.cpp function and pixel_order.h had gone in reformatted in another style. Built on Linux and Windows; not run with an HDR game. The emulator and core must be from the same build.
- New core option HDR Output (experimental, off by default). With it on and the frontend's own HDR on (RetroArch: Settings > Video > HDR), the picture goes to the frontend as HDR10, PQ in Rec.2020 (RETRO_PIXEL_FORMAT_HDR10_2101010, asked for at load once RETRO_ENVIRONMENT_GET_HDR_METADATA says the frontend shows HDR and takes it; otherwise, or if it refuses, XRGB8888 as before). A game made for HDR is told the display can show it, and when it switches its output to HDR its picture, PQ already, goes through untouched; any other game, the splash, the FPS counter and the trophy pop-ups are turned into PQ in the output pass and ImGui's shader, as they look in SDR, with SDR white at the frontend's paper white. A frontend that cannot share the images gets the frame read back whole, ten bits a channel, put in XRGB2101010's order as it is copied into the shared memory (nothing rounded), and uploaded as such. The output pass is tested on lavapipe (libretro/tests/pq_output_device_test.c: SDR unchanged, PQ against SMPTE ST 2084 and the BT.2087 matrix worked out in the test, a game's HDR passed through), as is the reordering (libretro/tests/pixel_order_test.c); the ImGui shader is checked with spirv-val only. Not run on an HDR display, with RetroArch, or with a game that outputs HDR: unverified on hardware. The emulator and core must be from the same build (the shared memory's version goes up).
- The core had a second libretro.h of its own (libretro/libretro.h), years behind the one in libretro-common, and its own files built against it while libretro-common's built against the other. It is gone: everything builds against libretro-common's, which is RetroArch's. Needed for HDR (the HDR10 pixel format and GET_HDR_METADATA are only in the newer one). Also drops a stray comment opener in libretro_core_options.h that clang warned about. Built on Linux and Windows.
- libretro-common resynced with RetroArch (72e8b02): 15 files had fallen behind (libretro.h, retro_atomic.h, file_stream, the VFS, net_http, the AAC, H.264 and MP4 decoders), and two new headers they include (raac_tables.h, rh264_cavlc_tables.h) are added. Every file the core has is now identical to RetroArch's.
- Audio3D allocated memory while a game ran, every few milliseconds: a block for each piece of sound the game queued (each object and the bed), another for each mix, the queues themselves as they moved along (std::deque takes a chunk at a time), and a buffer for each block a game sent through a port it opened with sceAudio3dAudioOutOpen. All of it is now made when the port is opened (the blocks for as much sound as the port can queue at once: its queue depth for the bed, and for each of its objects plus the mix) or when an object is reserved, and used again after that. The pools and fixed queues are checked against std::deque here; not heard in a game.
- Copy GPU Buffers could give a black or broken picture (Sekiro on a base PS4). The copies of the game's command buffers were made in one buffer that was used again from the start each time the game submitted a frame, while the GPU thread could still be working through the frame before: the new copies were written over commands it had not read yet. Anything that slowed the GPU thread (a heavy scene, Dump Shaders' captures) made it likelier. The copies now go into three frames' worth of room, used in turn, and a frame's room is used again only once the GPU thread has finished every submission in it; with none free (the game three frames ahead) a submission is read where the game has it, as with the option off, and nothing waits. The room (60 MiB, made when the game starts, with the option on) is C89 (src/video_core/amdgpu/cmd_copy_ring.c), tested in libretro/tests/cmd_copy_ring_test.c: an unfinished frame's copies stay whole while later frames are submitted. Not run on the game.
- A game that outputs ten bits a channel (A2R10G10B10, plain or sRGB) reaches the frontend with all ten: the frames the picture is drawn into and handed over in are A2B10G10R10 instead of B8G8R8A8, which halved its precision to eight bits, so smooth gradients (skies, fog, dark scenes) could band. An eight-bit game's picture is unchanged by it: it fits the wider format exactly, in the same four bytes a pixel. RetroArch draws from a frame image of any format. A frontend the images cannot be shared with still gets XRGB8888, narrowed once from the ten-bit frame on the GPU by a blit, which rounds to the nearest step; a device without the ten-bit format's features (Vulkan requires them of all) keeps eight-bit frames, and one that cannot export ten-bit images reads them back. Tested on lavapipe (libretro/tests/frame_narrow_device_test.c: the format keeps ten bits, the readback gives B, G, R rounded). Not run on a GPU, or with RetroArch. HDR is not passed on yet (AGENTS.md says what that takes).
- The custom trophy sound, when it is an MP3, is decoded to float and resampled from that, so it is rounded to 16 bits once, in the mix, rather than also when it is decoded. The resampler takes a float source for it (audio_mix_resample_f32, tested in libretro/tests/audio_mix_test.c). Music stays decoded to 16 bits for now: decoding a whole track to float would double its memory, and AGENTS.md says how that is to be done instead.
- Sound and the pad's sticks lost precision in the core's own handling, which is now looked for in every change (AGENTS.md, Quantization). Every source in the core's mix (each audio port, Audio3D, the music player, the trophy sound) was cut to 16 bits on its own, towards zero, and the sum cut again: quiet passages had the step around silence twice as wide as the others, and two quiet sources could add up to silence. The mix now keeps every source as floats and rounds the sum to the nearest 16-bit step once, as it is handed to the frontend. Audio3D's mix was also cut to 16 bits, at a scale of 32767 where the rest of the path uses 32768, before going through a 16-bit port: it now goes through a float port, whole, with one buffer less for each block. A stick at rest read as 127 instead of the pad's centre, 128 (the value was cut down rather than rounded), so a game that reads a stick without a dead zone saw it a little off to the left and up; sticks and triggers are now rounded, the same either side of rest. Tested: libretro/tests/audio_mix_test.c (rounding of both signs, the ends, a sum of two sources under half a step each) and libretro/tests/pad_scale_test.c. Not heard or played here.
- With Dump Shaders (diagnostics) on, a game could lose its picture for good once a frame had been written out (Sekiro on a base PS4: black, with only the HUD). Reading back each image's pixels waited for the GPU, which ended the command buffer after every image; a frame with a hundred of them then counted as a hundred frames to everything that ages by submissions, and images still in use were taken for stale and dropped, among them ones that carry state from frame to frame. The pixels are now written when the GPU has done the copy, in its own time, with no wait and no extra submission. Not run on the game; with the option off none of this code runs.
- Game's Sample Positions is off unless switched on, and is a new option (the old one's saved value is not carried over). It has never been run on a GPU, and with it on a multisampled depth buffer has to carry its sample positions through every change of layout or Vulkan leaves its contents undefined: while Sekiro's black scene on a PS4 Pro is being looked for, that is one unknown too many. The frames Dump Shaders writes out are no longer picked by their number, which twice gave only a loading screen: the first written is the frame after one with 400 draws or more, and two more follow five seconds apart.
- The frames Dump Shaders (diagnostics) writes out go to a folder of their own, shadPS4/shader/frames, so they can be sent without the thousands of shader files next to them (an archive of the lot is too big to send, and arrived cut off twice). Three frames are written, the 1800th, 2700th and 3600th the game shows: the 900th was a loading screen in Sekiro, with nothing drawn. An image's pixels are thinned to at most 128 across.
- Sekiro on a PS4 Pro still shows the red wash (the base PS4 picture is back). What the game asks for in a frame is known now and nothing in it stands out any more, so the next thing to look at is what is in the images. A frame written out by Dump Shaders (diagnostics) now comes with the pixels of every image a shader reads in it that the GPU wrote: each once, as it is when a shader first reads it, read back and thinned to at most 256 across, in frame_<number>_img<n>_<address>_f<format>_<w>x<h>_s<step>.raw next to the frame's text, which notes each. With them the pass where the scene turns black can be seen instead of inferred. Four frames are written now (the 900th, 1800th, 2700th and 3600th the game shows) instead of sixteen, to keep the files small. Built on Linux and Windows; the game is not run here.
- Sekiro on a base PS4 lost its picture (black, with only the HUD and the red edge) after the depth block's copy went in. That copy is now done only for a multisampled depth buffer, which is what it was written for (the PS4 Pro checkerboard); with one sample the draw runs with its own shader, as it did before. Why the copy broke the base picture is not established. One fault in it is put right, and may be the reason: it wrote all four channels of the colour target, the copied value in the first and zero in the others, whatever the game's write mask said. The hardware puts depth in the colour's red and stencil in its green and writes only the channels in the mask (Sekiro copies depth with the mask on red and stencil with it on green), so a target that held something else in its other channels was wiped. The copy now takes the plane from the mask and writes only the masked channels. Built on Linux and Windows; not run on the game.
- Sekiro on a PS4 Pro, the red wash: the frame written out by the last change shows one image in the whole frame that a shader reads and nothing ever fills. The compute shader that puts the checkerboard together (0x567a884f) reads, next to the frame's colour, a two-sample 32-bit integer image of the frame's size and compares its values between a pixel and its neighbours: the PS4 Pro's ID buffer, which that console's GPU writes by itself while geometry is drawn (which object and triangle each sample belongs to) and which the core does not have. A multisampled image is not read from the game's memory, so that image held whatever the GPU's memory held; where the values of a pixel and its neighbours differ the shader's bounds stay at infinity, and its output, fed back frame after frame, went to infinity everywhere. A multisampled colour image that nothing has drawn into is now cleared to zero before a shader reads it, so the checkerboard is put together as if every sample belonged to one object: softer edges than with the real IDs, but a picture. The ID buffer itself is not emulated yet; to find how the game sets it up, a written frame now also lists the registers each draw is asked with that changed since the draw before. Built on Linux and Windows; not run on the game.
- Sekiro on a PS4 Pro still shows the red wash with the last two changes in (the depth block's copy, the game's sample positions), so what the game asks of the GPU in a frame is now written out instead of guessed at. With Dump Shaders (diagnostics) on, every 900th frame the game shows (16 of them, so the first four minutes) is written to frame_<number>.txt next to the shader dumps: a line for each draw the game asks for with its shaders and the registers that decide what becomes of it (depth block control, EQAA, sample counts, masks and positions, colour control), each texture a shader is given (what the game named, which image it was bound to, that image's samples and whether the GPU ever wrote it), each colour and depth target with its registers, and every copy, clear, resolve, upload and change of an image's sample count. These are the notes kept for the report of a lost device, which now also go to the file while one is open. Nothing is written with the option off.
- A game's own sample positions. A PS4 game can say where in a pixel each sample of a multisampled pass sits, differently for each pixel of a two by two block (the PA_SC_AA_SAMPLE_LOCS_PIXEL registers); the core did not read them and every pass had Vulkan's positions. Sekiro's checkerboard on a PS4 Pro depends on them: its resolve shader takes the one shaded sample of a pixel to be on the left on one row and on the right on the next, swapped every frame, so with fixed positions every other row is drawn half a pixel off (stair-stepped, shimmering edges). A pass whose positions the game has set to something other than Vulkan's now gets them through VK_EXT_sample_locations, over a two by two block where the GPU allows that (else the first pixel's for all), and a depth buffer drawn that way carries the positions through its layout changes, as Vulkan requires. Passes with no positions set, or exactly Vulkan's, are untouched. New core option Game's Sample Positions (on by default) switches it off. The reading of the registers is tested (libretro/tests/sample_locs_test.c); lavapipe has no VK_EXT_sample_locations, so nothing of the Vulkan side has been run: built on Linux and Windows only, unverified on any GPU.
- Sekiro on a PS4 Pro, whose picture was a red wash with no scene in it: the game's shader dumps show why. Its checkerboard rendering keeps depth and stencil with two samples for each pixel and, each frame, has the GPU's depth block copy one sample of the depth buffer into a float colour target and of the stencil into an integer one (DB_RENDER_CONTROL's depth copy and stencil copy, with the sample to copy), drawn with a pixel shader that writes nothing but zero; the rest of the frame (lighting, the smaller depth buffer, the checkerboard resolve) reads those copies. The core did not know the copy and ran the draw as an ordinary one, so both targets were all zero: every pixel at one depth. Such a draw now copies the plane (depth to a float target, stencil to an integer one) of the sample the game names into the first colour target. The register's sample field was also one bit wide where the GPU has four. On a base PS4 the game reads its one-sample depth buffer directly, which is why that looked right. The copy's shader is tested on lavapipe (libretro/tests/depth_to_color_device_test.c: each sample of a one- and a two-sample depth buffer, depth and stencil); the game itself is not run here, so whether this is all that was wrong with the picture is not known. Still not done for this mode: the game moves the sample positions from row to row and frame to frame and the core leaves them where Vulkan has them, which will show as stair-stepped edges.
- New core option Dump Shaders (diagnostics): every shader a game uses is written as the game has it (.bin) and as it is given to the GPU (.spv) to shadPS4/shader/dumps under the frontend's system directory. The core could do this but there was no way to switch it on. For Sekiro on a PS4 Pro, whose picture is wrong: with its shaders in hand what each pass does can be read instead of guessed.
- Sekiro on a PS4 Pro: the change that built a per-sample fragment shader to run once under one colour sample is taken back. With it the game lost the GPU device before getting in game, at a draw (vertex shader 0xc958709d, fragment shader 0x41164f0f) in a pass of two colour targets of one sample over a depth target of two; why is not known. A per-sample pass with fewer colour samples than depth samples again gets as many colour samples as depth, which gets in game but with the picture wrong (the low-health overlay over everything). The checkerboard rendering of the Pro is not right yet in either form; with PS4 Pro Mode off the game renders as it should. The checkpoint on every draw stays out. Built on Linux and Windows.
- Sekiro stopped after a cutscene with 'dcb copy buffer out of reserved space': with Copy GPU Buffers on, the copies of the game's command buffers had room for 2 MiB between two flips and the game submitted more. The room is now 16 MiB, and commands past it are read where the game has them (as with the option off) instead of the emulator stopping. Built on Linux and Windows; not run on the game.
- Sekiro on a PS4 Pro (its checkerboard rendering: one colour sample under two depth samples) now renders that pass as the PS4 does where the GPU can mix sample counts (NVIDIA). The PS4 shades each colour fragment, so a fragment shader that asks to run for each sample runs once for a pixel there, as sample 0; the core let it run for each sample, which lost the GPU device, and the change before this one gave the pass two colour samples instead, which got in game but with the picture wrong (the low-health overlay over everything). The shader is now built to run once: the sample's number reads as 0 and inputs taken at the sample are taken at the centroid, with sample shading off, and the targets stay as the game has them. A GPU that cannot mix sample counts renders as before. The checkpoint on every draw that was there to find the fault is gone (a draw is still noted, for the report of a lost device). Built on Linux and Windows; unverified on hardware.
- Sekiro lost the GPU device after its intro movie. The last report names the draw and what it drew into: a full-screen pass over a colour target of one sample and a depth target of two (the game's checkerboard rendering), with a fragment shader that runs once for each sample. On a GPU that can mix sample counts (VK_NV_framebuffer_mixed_samples: NVIDIA) the pass was given the targets as they are, which that extension does not allow together with per-sample shading: the second sample's colour has nowhere to go, and the driver's fault was a write to address nothing. A pass whose fragment shader runs per sample (it reads the sample's number, or an input taken at the sample) with fewer colour samples than depth samples now gets as many colour samples as depth, as every pass does on a GPU that cannot mix them. The draws before it in the same pass, which do not shade per sample, ran. Built on Linux and Windows; unverified on hardware.
- Sekiro's lost GPU device is now down to one command: a full-screen draw (vertex shader 0x8a597eb9, fragment shader 0xcd0c2bb6) is the last thing the GPU began, in a pass with a depth and a stencil attachment, and the driver's fault is a write to address nothing. A pass was given a depth or a stencil attachment whenever the game's registers named a format for one, whether or not the image behind it has that plane; it now gets only the planes the image has. That is the one way found for a pass to write to a plane that is not there, and it fits the address, but it is not known to be what Sekiro does. The report of a lost device now also writes the 24 notes before the last operation the GPU reached, and each pass notes its colour and depth targets (address, format, samples, layout, size, the planes asked for and had) and each draw what its fragment shader writes. Built on Linux and Windows; unverified on hardware.
- The report of a lost GPU device named the last operation the GPU reached (Sekiro: the detiling of a 1600 by 1800 image at 0x2bee60000, so not the tiling that was suspected) but not what came after it, where the fault is: only the last 32 notes were written, a hundred too late, and draws, uploads and render passes were not noted at all. Now every draw, render pass, upload, image copy, resolve, clear and blit is a note and a checkpoint too, the ring holds 4096, and the report writes what was recorded from the last operation the GPU reached on (160 of them), then the last 16. The checkpoint on every draw is there to find this fault and is to come out again. Built on Linux and Windows; unverified on hardware.
- Sekiro still loses the GPU device after its intro movie with the two holes of the last change closed (the driver again: a write to an invalid address), so the report of a lost device now says what the GPU was doing. Each compute dispatch, tiling and detiling, copy and fill of a buffer and copy of an image into a buffer is noted as it is recorded (what it is and the numbers that say which: the shader, the image's address, size and tiling, the buffer's offsets), in a ring of 256 that costs a few stores; where the driver has VK_NV_device_diagnostic_checkpoints (NVIDIA) each is also a checkpoint, and the report names the last one the GPU had begun and the last it had finished, then the last 32 that were recorded. Nothing is written to the log until a device is lost. Built on Linux and Windows; the checkpoints are unverified on hardware.
- Sekiro lost the GPU device after its intro movie; with the last change the driver says why: a write to an invalid address. Two places could write where nothing is, and both are closed. A shader that reads the guest's memory through a pointer (direct memory access) took any 64-bit value for one: an address outside the guest's 40-bit address space was looked up past the end of the page table, and marking it as a fault wrote past the end of the fault buffer. Such an address now reads as nothing (zero, or the copied constants) and touches neither. And the tiling compute shader, for a texel past the image's last mip, took that mip's size and pitch from whatever follows the mips and wrote (tiling) or read (detiling) anywhere: under lavapipe that is a write through index 0xffffffff, a crash every time (libretro/tests/tiling_device_test.c runs the shader on a device and checks it; it crashes on the shader as it was). Such a texel, and one whose place is past the end of the tiled data that is bound, is now left alone, and a mip with no pitch or height no longer divides by nothing. When an image a compute shader reads as a buffer is tiled back into the guest's memory, all of it is backed first, not only the range that was asked for, and an image that runs past its arena is left. Which of these Sekiro hit is not known: the first is the likely one (its shaders use that kind of read), but nothing here can run the game. Built on Linux and Windows; unverified on hardware.
- libSceNgs2: the rest that was missing. A custom sampler rack's modules now run on what the sampler plays (they were skipped). Peak meters: a sampler, a submixer and the mastering voice measure the loudest sample or the root mean square over as many grains as the rack was made to keep, once the game switches the meter on, and report it in the voice's state (the mastering voice per channel, for what comes in and what goes out, with the limiter's peak and gain; a submixer with its envelope's and compressor's height); a custom rack has the peak meter module 0x1a, and a module's state is written where the rack's option says. A meter that is off reports 0, as on a console: until now a voice's peak was always measured. The helpers, which did nothing and said OK: sceNgs2ParseWaveformData, File and User read a RIFF WAVE (PCM of 8 to 32 bits, float, ATRAC9) or a VAGp for its format, its size and the blocks a sampler plays, with its loop as a block that repeats; sceNgs2CalcWaveformBlock and sceNgs2GetWaveformFrameInfo; sceNgs2PanInit and sceNgs2PanGetVolumeMatrix; sceNgs2GeomResetListenerParam, ResetSourceParam, CalcListener and Apply. They are C89 (src/core/libraries/ngs2/ngs2_util.c) with a test of their own (libretro/tests/ngs2_util_test.c); a file is read with libretro-common's file_stream. Known from readings of the console's library: the waveform parsing, the block and frame arithmetic, panning, the listener's matrix and the reset values. The core's own: what sceNgs2GeomApply makes of distance (inverse, by the rolloff factor, whatever the model), cone, Doppler and radius, and the 0x1a module number. Built on Linux and Windows; not yet run on a game.
- libSceNgs2: envelopes, the compressor, distortion, the limiter and the delay, chorus and pitch shift modules, which so far let their sound through unchanged. A sampler or a submixer takes an envelope (up through its forward points when it plays; told to stop, it goes down through its release points first and stops at their end), and the envelope's height is what a sampler's state reports. A submixer takes a compressor and a distortion, a sampler a distortion, the mastering voice a limiter. In a custom rack the modules 0x10 envelope, 0x11 distortion, 0x12 compressor, 0x1c chorus, 0x1d delay and 0x20 pitch shift work (Dead or Alive Xtreme 3's 'MultiFx' rack has a 0x12). The delay's and chorus's lines are laid out with the rack, in the game's buffer: nothing is allocated while a game plays. Known from a reading of the console's library: the compressor (levels over 32 samples, peak or mean square, threshold and ratio, knee, flag 1 off, flag 8 the LFE apart). The core's own, and not sure to sound as on a console: the distortion's curve (a*x + b*x^3, gated and clipped), the limiter, the delay, the chorus and the pitch shift (two readers of a short line, cross-faded), every envelope curve as a straight line, durations as samples and delay times as seconds. A custom sampler rack's modules are still not run. ngs2_core_test checks each against what it has to give. Built on Linux and Windows; not yet run on a game.
- When the GPU's driver gives the device up (Sekiro ends so after its intro movie on an RTX 5090: "Failed to get master semaphore value: ErrorDeviceLost"), the log now has the driver's own account of it: its description, the addresses it faulted on and the vendor's codes, from VK_EXT_device_fault where the driver has it, as critical lines, which are written whatever the log's level. Nothing was said before but that the device was gone, at the place the emulator next asked the driver something, which is not where the fault was. The reader is C89 (src/video_core/renderer_vulkan/vk_device_fault.c). This finds the cause; it does not mend it. Built on Linux and Windows; a lost device not yet seen with it.

- Bloodborne's vertex explosions (shadPS4 #1232: the player and humanoid NPCs thrown into sheets across the screen), at their source, with GPU readbacks left off. The game has the GPU write some of its vertices (compute shader output), and with readbacks off those bytes exist only in the buffer cache, with stale ones beneath them in guest memory. When the game then wrote anything else in the same 4 KiB page, the whole page was uploaded from guest memory and the GPU's vertices were replaced with the stale ones. Readbacks Relaxed, the usual answer (and the bloodborne_linux fork's default), avoids it by having the game's thread wait for the GPU to hand the bytes back at each such write, at up to half the frame rate. Now the page is kept as it was just before the write (write_snapshots.c, C89: a fixed table of 2048 pages made once, lock-free, a page of it resident only once used), and its upload sends only the bytes the game changed since, in 4-byte cells, and everything outside the GPU's ranges as before: the GPU's vertices stay, memory the game takes back for its own data is uploaded as it writes it, and nothing waits on the GPU. - VulkanMemoryAllocator is gone (externals/vma, a submodule, and its 20 000-line header compiled into the core). The renderer's device memory comes from a heap of its own, vk_heap.c, in C89: memory is taken from the driver in blocks of at most 64 MiB (an eighth of a small heap), the first of a kind 8 MiB and doubling as they fill, where VMA's were 256 MiB (its first ones 32 MiB); a request over half a block, a buffer with a device address (as before) or what the driver wants alone gets memory of its own. A free piece is found through 64 lists by size class and a bit mask (two-level segregated fit), freed pieces merge with their neighbours at once, and one empty block of a kind is kept for reuse, the others given back. The pieces and blocks are fixed tables made when the device is, touched only as they are used, so nothing is allocated from the C heap mid-game, where VMA allocated its bookkeeping as it went. A host-visible block is mapped once, the first time a piece of it is wanted mapped, and a buffer's mapped memory is that one mapping at its offset, lent with no copy; a piece of noncoherent memory is whole atoms, so a flush or invalidate never reaches a neighbour's. The type for each kind of buffer and image is chosen as VMA chose it (device local preferred, a mapped stream buffer in host-visible device memory where there is some, readbacks in cached memory), images and buffers keep to separate blocks where the device's bufferImageGranularity asks, and the budget comes from VK_EXT_memory_budget as before, read again every 32 blocks made or freed, a new block made smaller to fit in it before an allocation goes over. An image or device buffer refused for the budget is no longer put in system memory, where VMA put it when the device's budget was used up and where it stayed, read over the bus, until it was freed (a fork of shadPS4, bloodborne_linux, saw an RTX 4060 fall to 17-27 FPS from it until the game was reloaded): the refusal goes back to the texture or buffer cache, which asks again over the budget, still in device memory; system memory is used only where the driver itself has no device memory left, so a small card still runs. Taking and giving back memory run in a Common::Combiner; images and buffers are created and bound outside it, and flushes take nothing. The heap tested on its own against a stub driver under AddressSanitizer, UndefinedBehaviorSanitizer and ThreadSanitizer (libretro/tests/run.sh): type choice, alignment, merging, block growth, own memory, atom widening, the budget, no spill to system memory over the budget, a driver out of memory, and 100 000 random allocations never overlapping. Not yet tested on a GPU or a game.

- Sound output and input take no lock. The audio port tables were arrays of shared_ptr under a shared_mutex; they are Common::SharedSlots now (new: a slot is read with libretro-common's retro_retire, so a read never waits on an open or a close). Each output port's buffer is handed between the game and the port's thread with an atomic flag and a retro_eventcount where the game waits for it to drain; the port's mutex was held by its thread while it waited up to 250 ms for the frontend to take sound, keeping the game's next sceAudioOutOutput, and its volume changes, waiting as long. The game's calls on a port, and opening and closing, run one at a time in a Common::Combiner. sceAudioInOpen no longer looks one past the end of the input port table when every port is taken. SharedSlots tested on its own under AddressSanitizer: two threads putting and taking 300 000 objects while four read them, every read the right object and none left over. Not yet tested on a game.
- The controllers take no lock. Every button press and stick move from the frontend, and every read of the pad by the game, took the controller's mutex. A change, and a read of the report history, now runs in the controller's Common::Combiner; scePadReadState takes the state as last reported through a retro_seqlock, so it neither waits on the input thread nor holds it up. Not yet tested on a game.
- Video output takes no lock. The flip queue between the GPU thread and the present thread was a std::queue under a mutex; it is a retro_spsc ring now (the GPU thread runs every flip, so it is the one writer). The flip and vblank status the game reads were copied under two mutexes the present thread took for every update; the present thread now writes its part under libretro-common's retro_seqlock (new in RetroArch's libretro-common) and the counts the submitting threads change are atomics, so a read never holds up a flip. sceVideoOutWaitVblank and the GPU thread's wait on a flip label park on retro_eventcount instead of condition variables. The flip and vblank event queue lists, which the game changed while the present thread walked them with no lock at all, are fixed slots taken and freed with a compare-exchange. Not yet tested on a game.
- Graphics submissions take no lock. The game's submit, flip and SubmitDone calls were serialized by a mutex, and the wait for the GPU to go idle after a SubmitDone was a second mutex and a condition variable shared with the GPU's idle interrupt. The submissions now go through Common::Combiner, new: each caller queues its submission on a lock-free mpsc_stack, and whichever caller finds no one running them runs all that are queued, in order, while the others park on a retro_eventcount until theirs is done; nothing is allocated. The submission lock is an atomic, taken before the GPU is looked at and released by whichever of the submitter and the interrupt sees the GPU idle last, and the waits park on a retro_eventcount. Combiner tested on its own with eight threads running 2.4 million functions: never two at once, each thread's in order, clean under ThreadSanitizer. Not yet tested on a game.
- The GPU command processor takes no lock. Submissions from the game's threads (graphics, constant engine and compute), commands from the video output and the buffer cache, and the waits for the GPU to go idle all went through one mutex and condition variable shared with the GPU thread, which took it, and each queue's own mutex, twice for every slice of work it ran. Submissions and commands are now pushed onto libretro-common's lock-free mpsc_stack, which the GPU thread takes into lists only it touches; the GPU thread, a sender waiting for its command and WaitGpuIdle park on retro_eventcount, and a command that is waited for no longer allocates. Tested on its own with four threads pushing 800 000 submissions and commands, waited for and not, against one consumer: every one ran once, in order per thread. Not yet tested on a game.
- The picture is handed to the frontend on the GPU, always: the core option GPU Frame Hand-over is gone, and what it did is how the core works. RetroArch draws the emulator's own images, and its statistics show the frames as hw, where each 1920x1080 frame was read back, copied into the shared memory, handed over as a software frame and copied again by RetroArch's threaded video (about 300 microseconds a frame for that last copy alone) before being uploaded. The core asks for a Vulkan context whatever the frontend's video driver, so RetroArch switches to `vulkan` as it does for any Vulkan core. Where the images cannot be shared with the frontend's device (another GPU or driver, or no memory import), the picture no longer stays black: the emulator reads its frames back and the core uploads each into an image of the frontend's device, with the reason in the log. Only a frontend that gives no Vulkan context gets software frames.
- The core is ParaLLEl PS4: parallel_ps4_libretro (.so, .dll, .info) where it was shadps4_libretro, and its launcher parallel_ps4_libretro_host. The frontend files its options, remaps and overrides under the new name, so they start from the defaults; the core options keep their keys, and everything the core keeps stays in system/shadPS4/.
- The core builds against msvcrt, the C runtime of MSYS2's MINGW64 shell, which has no quick_exit: Common::QuickExit and Common::AtQuickExit keep the handlers themselves there (32, run newest first, then _exit) and are std::quick_exit and std::at_quick_exit everywhere else. The whole core built and linked against MINGW64's GCC 16 runtime as well as UCRT64's.
- The static Makefile builds the Windows core too, with MinGW-w64: in an MSYS2 shell (UCRT64, MINGW64 or CLANG64), or across from Linux with CC and CXX set to a MinGW-w64 compiler. It treated an MSYS2 shell as Linux and stopped at the Linux launcher, which Windows does not use (rundll32 starts the emulator's process there). Built and linked with clang 19 against MSYS2's UCRT64 GCC 16 runtime and mingw-w64 14; the DLL loads under wine and exports the libretro functions. Fixed on the way: ntapi.h had offsetof without <cstddef>, Common::FS::CopyFile collided with windows.h's CopyFile macro (gone: CopyAll copies a file as well), and libretro-common's fopen_utf8.c, which the Windows VFS calls, was not in the source lists.
- Closing the content on Linux returns as soon as the emulator's process has ended. The core looked every 10 ms for up to three seconds, on the frontend's main thread; it now waits on a descriptor for the process (pidfd, Linux 5.3 and newer), with the 10 ms look kept for older kernels.
- A game thread waiting on an event queue's high-resolution timer no longer keeps a CPU core busy. It yielded in a loop until the timer was due, for the whole wait; it now sleeps until shortly before (0.2 ms on Linux, 1 ms on Windows, where a timed sleep can oversleep) and yields only for that last stretch, and a timer added or removed meanwhile wakes it to look again. Measured over a hundred 5 ms timers: due within 0.04 ms, at 2 % of a core where it took all of one.
- The emulator's process no longer wakes on timers to see whether the frontend has done something. Its sound, controller, frame and control threads looked at the shared memory every 1 to 20 ms; they now park on libretro-common's retro_shared_eventcount (new in RetroArch's libretro-common: a futex on Linux, a named semaphore on Windows) and the core wakes them when it writes: sound is mixed as soon as the frontend has taken some or a source hands some over, a button press reaches the game at once instead of up to 2 ms later, a frame waiting for an image to draw into starts as soon as the frontend lets one go, and closing the content or changing an option is acted on at once. The controllers' 4 ms reports keep to real time instead of drifting with the sleeps. The frontend is handed the sound straight from the shared ring instead of a copy of it each frame.
- No file or folder operation is left on std::filesystem: startup and mounting, save data (listing, sizes, free space, icons), fonts, trophies, patches, custom modules, USB storage, additional content, shader dumps, the pipeline cache's listing, PKG install checks and the PKGs found beside a game all go through libretro-common, with names in UTF-8 on every host. Save data's free space check and the PKG install's use path_get_free_space; a PSF's time is the file's modified time as stored, where it was converted between clocks.
- The game's file system calls go through libretro-common instead of std::filesystem: mkdir, rmdir, stat's folder times, truncate, chmod, the host folder listing behind getdents, the existence and type checks the mount stack makes for every path a game opens, the case-insensitive lookups, and the update and mod folder probes. A folder listing takes each file's size from the listing itself (the find data on Windows) where it took a stat per file, and names are UTF-8 on every host. chmod keeps what a host can keep of a mode, whether the file can be written, where it set the POSIX bits as given (mode 0 left the file unreadable to the emulator itself).
- Renaming a file or folder in a game moves it instead of copying it. sceKernelRename and rename copied the whole source, folders recursively, and then deleted it, on every host, because Windows will not move a file that is open; a save folder rename read and wrote every byte of it. It is now a rename, with a file the game has open closed for the move and opened again at its new name, and a copy only when the two names are on different file systems.
- Folder trees are removed, copied and measured through libretro-common (path_remove_tree and path_copy_tree, new in RetroArch's libretro-common, and retro_dirent) in place of std::filesystem: save data deletion, save backups and restores, the temporary data folder, trophy extraction cleanup, PKG installs and the game size shown for save data. Each file in a copied tree is cloned where the file system can. libretro-common synced with RetroArch.
- The pipeline cache's writer is lock-free and no longer loses blobs. A save from a shader compile took two mutexes and a condition variable, and wrapped the blob in a packaged task in a std::queue; it now pushes one node onto libretro-common's lock-free MPSC stack and wakes the writer on an eventcount, and the writer writes them in the order they were saved. The request count both threads changed was not atomic, and closing the cache (at the end of a session) stopped the writer with saves still queued, which were then never written; closing now waits out saves already under way and the writer finishes what it was given before it stops.
- A static Makefile, as parallel-ps2 and parallel-gx2 have: `make` builds the core with no CMake, for Linux x86_64 and aarch64 (with box64's parts or FEXCore, as the CMake options). It makes what CMake generated itself: the version file from git, the ImGui fonts with ImGui's own tool built for the build machine, the launcher carried in the core, and the embedded files. libusb is built with netlink for hotplug, so the core needs no libudev. Objects go under obj/<platform>-<arch>, a change of compiler or options starts that tree afresh, and the submodules are fetched if the checkout has none.
- The files the core carries (trophy icons and sound, notification icons, the AMD reciprocal tables) are a plain C table made by the build (cmake/EmbedResources.cmake, libretro/embed.sh) in place of CMakeRC, which is gone. They are lent where they lie: a notification icon was copied into a vector and then copied again on the way to the decoder.
- The core builds again: dropping RenderDoc took the captures folder out of the paths list but left it in the C side's copy of the list, whose order must match, so c_bridge.cpp failed its check.
- Overlay textures (icons, the splash, trophy and save data pictures) no longer stall the GPU. Each upload waited for the whole queue to go idle, on the thread that draws the frames, and each destroyed texture waited for the whole device. An upload is now submitted with a fence and shown once the fence has signalled; a destroyed texture's image, view and descriptor go once fences submitted on the queues that may still draw it have signalled. Nothing waits; the render thread polls the fences once a frame.
- Asynchronous I/O is asynchronous. sceKernelAioSubmit* read or wrote every request before returning; a submit now hands its requests to a worker thread and returns at once. Each submit id is a batch slot made up front, game threads push batches onto libretro-common's lock-free MPSC stack, and the worker does them in submit order and wakes the waiters on an eventcount, where the wait functions polled every 10 microseconds. Cancelling marks a batch aborted and the worker skips what is left of it. sceKernelAioWaitRequests honours its mode (all or any). No lock and no allocation while a game runs.
- The PKG reader no longer needs OpenSSL, which nothing linked since LibreSSL went, so a core with it failed to load. It uses libretro-common's crypto: AES-XTS (new in RetroArch's libretro-common, eight blocks at once on AES-NI and the ARMv8 crypto extension) for the PFS sectors, AES-CBC for the encrypted entries, SHA-256, HMAC-SHA256, and RSA with libretro-common's big numbers for the two key unwraps. Checked against OpenSSL for every primitive. libretro-common synced with RetroArch.
- Fewer copies on the file paths. A game's read of a mapped file (its own data) or of a file in a ZAR archive or a PKG goes straight into the game's buffer, where every read went through a bounce buffer and was copied again; only a read through a read() system call, which a protected page would fail, still takes the bounce. A PKG is mapped and its sectors decrypted from where they lie, with the XTS key set once instead of for every 4 KiB sector; a whole 64 KiB block a read asks for is decoded straight into the caller's memory; the block cache is made once, in place of a new vector for each block read and each block decoded; and a PKG entry is read from the mapping, decrypting only the blocks asked for, where every read of one read the whole entry and the PKG's table again. PNGs for the overlay are decoded straight into the texture's upload buffer. The pipeline cache's writer no longer copies each blob into its request.
- PKG Content's Install no longer holds up the frontend. The PKGs are extracted on a thread of their own, and the content loads at once: the core shows black, with the install's progress in the frontend's progress messages, and starts the game when the install is done. A failed install is reported as before and the content is closed. Closing the content during an install stops it after the block being written. The worker and the frontend's thread share only the install's state, through atomics.
- File I/O goes through libretro-common's file streams. `Common::FS::IOFile` is a thin wrapper over an `RFILE` (no more `FILE*`, `fstream` or `fopen` anywhere in the core), with hints for the two common shapes: `Mapped` (a read-only file is memory mapped, and `Mapped()`/`View()` lend its bytes in place) and `Sequential` (written or read once, front to back, with no stdio buffer in between). The VFS has no append mode, so Append opens the file keeping its contents and every write goes to its end. Writes are no longer flushed one by one; the guest file system still flushes each guest write, so other handles see it at once, as on the console, and a read-only mount's files (the game's own) are mapped and read from where they lie.
- No more slurps: a whole file is a `Common::FS::FileView`, its bytes lent from a mapping, or, for an archive or PKG entry, the buffer it was decoded into, and the mount stack's `ReadFile` returns one. The pipeline cache's blobs (pipeline keys, shader metadata, SPIR-V), shader patches, PNGs (splash, save data and trophy icons, devtools), music and trophy sounds, param.sfo, RIF licences, npbind.dat, playgo-chunk.dat, TRP trophies (straight out of an archive too, where they were dumped to a temporary file first), the PKG keys and a PKG's param.sfo are read where they lie. Fonts share one mapping, or one decompressed copy of a built-in font, between every face open on them, where each face copied the bytes, and a font in the game's own memory is read in place. Byte-by-byte `istreambuf_iterator` reads (trophy icons, shader patch sources, the PKG marker) and the serializer's accidental copy of every archive it was given are gone.
- Writes are written whole: save data backups and the PKG install use the VFS's copy and unbuffered writes, play_time.txt is replaced atomically, the custom trophy notice is written only when its text changed, and the files the aarch64 build carries are written straight from where it carries them.
- glslang is gone, along with the `externals/glslang` submodule, so the build no longer compiles GLSL at all (and the Windows cross build no longer builds a host glslang). The renderer's own shaders, the full-screen triangle, the output pass, the MSAA copies, the fault buffer pass and the tiler and detiler, are written straight as SPIR-V words by C89 code (`video_core/host_shaders/host_spirv.c`), when a pipeline is made: on the stack, with nothing allocated. What were specialization constants (the fault buffer's page size, a tiling mode's parameters) are folded into the module, so a tiling shader holds only the arithmetic its mode needs. Tested against the GLSL shaders on lavapipe: the same pictures, fault lists and tiled and detiled bytes for every pixel width, micro and macro tiled, across tiling modes. Game shaders were already translated from GCN straight to SPIR-V.
- FSR is gone: the FSR Upscaling, FSR Sharpening and FSR Sharpening Strength core options, their settings, the devtools menu and the AMD FidelityFX sources. A picture is scaled to the output size by the output pass, which still sRGB-encodes it, decoding sRGB input first, and passes HDR through. The IPC's FSR commands are read and ignored.
- macOS: the core no longer bundles a Vulkan loader and the KosmicKrisp driver, and `externals/vulkan-loader` and `externals/mesa-kosmickrisp` are gone. The emulator takes the Vulkan its environment provides, as RetroArch sets it up; the `ENABLE_SYSTEM_VULKAN` option, the copy of the loader, driver and ICD next to the core, the `VK_DRIVER_FILES` override and the macOS 26 minimum that KosmicKrisp needed are removed.
- magic_enum is gone, along with the `externals/magic_enum` submodule. The names of the enums the core prints are C89 tables sorted by value (`common/enum_names.h`/`.c`), written by `src/common/gen_enum_names.py` from the values the compiler gives each enumerator; `enum_name()` finds a name by binary search, and `enum_name_exists()` and `enum_names_mask()` replace the range check and the IME flag masks. Names now come out for every value an enum has, where magic_enum gave none outside its default -128..128 range. IR opcodes use their existing `NameOf`. No enum reflection templates are instantiated any more, which takes that work out of the build.
- robin-map is gone, along with the `externals/robin-map` submodule. The pipeline cache's programs, compute pipelines and graphics pipelines are filed in `common/ptr_table`, a C89 hash table of pointers by a 64-bit hash: a lookup checks the full key, so two keys with one hash are both kept. The tables are sized up front for a large game. The descriptor heap's ready sets are a plain array and count per layout in a `u64_map`, and a new batch is allocated by Vulkan straight into it instead of into a temporary that was then moved in. The two file-system path caches, cold and behind a lock, use `std::unordered_map`.
- The intrusive list is now C89 (`common/intrusive_list.h`, builds as MSVC C89): a `list_hook_t` of two pointers and inline functions to link, unlink, splice, move, clear and count, plus `list_for_each` loops. `common/intrusive_list_cpp.h` only adds iterators for the C++ code that walks lists with range-for, and the hook's constructor and destructor; every change to a list goes through the C functions. The lists no longer keep a count.
- Boost is gone, along with the `externals/ext-boost` submodule. The last parts used were Boost.ICL and Boost.Pool. The buffer cache's range sets, the rasterizer's mapped ranges and the address space's usable regions are `IntervalList`s: sorted, merged intervals in one array, which gains a `Subtract`; the buffer cache's sets reserve room for 1024 ranges up front, where Boost.ICL allocated a tree node from a pool for each. The unused `RangeMap` and `SplitRangeMap` are removed. On macOS x86-64 the free LDT slots for thread TLS are a bitmap taken and given back with atomics, so the lock around them is gone.
- Boost.Intrusive is no longer used. `common/intrusive_list.h` has `Common::ListHook`, two pointers an element carries, and `Common::IntrusiveList`, a ring through them; inserting, erasing and splicing relink pointers and allocate nothing. A hook takes itself out of its list when its element is destroyed, so a list never points at a dead element. The IR's instruction lists, the structurizer's statement trees and the kernel's sleep-queue free lists use it. The control-flow graph's blocks, a Boost intrusive set, are now such a list kept in address order, with a sorted index built once for linking the blocks.
- Boost.Container and boost::hash_combine are no longer used. `common/small_vector.h` now holds `Common::SmallVector` (the first N elements in place, then the heap) and `Common::StaticVector` (at most N, all in place), plain buffers with a count whose iterators are pointers; they replace Boost's small_vector and static_vector and the earlier global SmallVector. `common/flat_map.h` has `Common::FlatMap` and `Common::FlatSet`, sorted arrays in place of Boost's flat_map, small_flat_map and flat_set. An IR instruction's list of uses is a `std::list`, the tile manager's key packs its four fields into two words before hashing, and an unused Boost include is gone from the SRT pass.
- protobuf and Abseil are gone, along with the `externals/protobuf` and `externals/abseil-cpp` submodules, so neither is built any more (the Windows cross build no longer builds a host protoc either). shadNet's messages are plain C89 structs with a table of fields each, written by `src/shadnet/gen_messages.py` from `shadnet.proto`, and encoded and decoded by `src/shadnet/pb_wire.c`, a small C89 implementation of the protobuf wire format. The bytes on the wire are unchanged: for every message, the encoder's output matches protobuf's byte for byte. Strings and bytes are not copied: a decoded field points into the packet it came from, and a request points at the caller's own strings. A decoded message's repeated fields are laid out in one block sized before decoding, where protobuf allocated each element and each string.
- The texture cache no longer uses Abseil's hash maps. Its sampler table, its set of images to read back and its table of metadata surfaces are a small C89 hash table (`common/u64_map`), linear probing with nothing left behind on erase, its keys, values and flags in one block. The sampler table is made once at the most samplers the GPU can hold, so it never grows during a game.
- RenderDoc support is gone, along with `externals/renderdoc`. The core no longer looks for RenderDoc at startup, no longer wraps each GPU submission in a capture, and no longer makes a `captures` folder; the `renderdoc_enabled` setting is removed. RenderDoc can still capture the core from outside, through RetroArch's Vulkan device.
- libretro-common synced with RetroArch: TLS handshakes can now be stepped without blocking, UPnP can reuse a gateway it found before and try other external ports, and an Adler-32 helper and a GIF image type were added. The core calls nothing new yet.
- FreeType is gone, along with the `externals/freetype` submodule. libSceFont and libSceFontFt read fonts with libretro-common's rtt, TrueType and CFF (CID-keyed included), in place from the bytes they were given: the system fonts the core carries, a game's font in memory, and a host font file read once through libretro-common's file streams. Nothing is copied and no library state is kept. Sizes, metrics, advances, kerning, outlines and bitmap boxes are worked out as FreeType works them out for an unhinted glyph, with the same 26.6 and 16.16 rounding, and match it number for number on the fonts tested. The coverage values inside a bitmap differ from FreeType's by under one level in 255 on average. A glyph's bitmap and outline buffers are kept and reused from one glyph to the next. Bitmap-only fonts are no longer read, and a missing character is no longer looked for in a font's other character maps; rtt picks the best Unicode one. Needs RetroArch's rtt points and components patch.
- The `half` library is gone, along with the `externals/half` submodule. The one half-float conversion the core made, turning 16-bit float clear colours into Vulkan clear values, uses libretro-common's `math/float16.h`, which gives the same exact values.
- Boost.Asio is no longer used. The kernel's event-queue timers ran on an Asio io_context, on a service thread woken through a mutex and condition variable. They now run on a timer thread of their own: arming a timer posts it to a lock-free ring, the thread keeps the armed timers in a heap reserved up front and sleeps on an eventcount until the first is due. Removing or re-arming a timer leaves the old entry to be dropped when it comes up, by a generation number, instead of cancelling it. Periodic timers still fire a period after the last firing, not after the callback ran.
- wepoll is gone, along with the `externals/ext-wepoll` submodule. On Windows a guest epoll is now a table of registrations polled with select() through libretro-common's `socket_poll`, which also takes more than 64 sockets now. Waiting threads read the table without a lock: each entry is a seqlock, written one at a time under the guest epoll's lock, and a one-shot entry is taken by one waiter only, by compare-and-swap. A change while a thread waits wakes it through the epoll's existing wake socket, so it polls the new set at once. The socket-pair and single-socket waits use `socket_poll` too, so a refused connect is reported straight away, where WSAPoll on older Windows never reported it.
- epoll-shim is gone, along with the `externals/epoll-shim` submodule. macOS and FreeBSD built and linked it, but the network layer already uses kqueue directly there, so nothing called it.
- The `date` library is gone, along with the `externals/date` submodule. It was built and linked on macOS and FreeBSD for a time-zone header that nothing used any more: the time zone comes from the C library's `localtime_r` there as on Linux.
- MP3 music plays gapless. libretro-common's rmp3 now reads the Xing/Info tag frame and LAME's encoder delay and padding: the tag frame is no longer decoded as a frame of silence, and the encoder's delay, the decoder's own 529 samples and the encoder's padding come off, so a track is exactly as long as what was encoded and loops without a gap. The track's length comes from the tag, so its buffer is allocated once at the right size.
- libSceAvPlayer's queues are lock-free. Packets, guest buffers and decoded frames move between the demuxer, the decoders and the game through libretro-common's waitable SPSC rings, one thread at each end, and a waiting thread sleeps on an eventcount instead of a mutex and condition variable. The guest buffers are made once at Start and the rings carry their indices, so nothing is allocated while playing. A decoder keeps a buffer it could not fill instead of handing it back. Stop closes the rings, which wakes every waiting thread at once. The event queue the controller thread reads is a lock-free ring as well. The demuxer's queues are now bounded: it waits when a decoder is 4096 samples behind.
- spdlog is gone, along with the `externals/spdlog` submodule. The log has one writer thread: other threads format a line on their own stack and post it through a lock-free ring, so logging takes no lock and allocates nothing (the thread name is now written into a buffer too). Files are written with libretro-common's file streams; the console keeps its colours. The settings keep their meaning: the per-class filter, the flush level, the session file with its size limit, append or truncate, and skipping duplicates. With sync logging (the default) every line is kept, a thread waiting only while the ring is full; with async logging a line that finds the ring full is dropped, and the count is logged. A critical line is always kept. Files are flushed whenever the writer runs dry, and `Flush()` waits until it has.
- cpp-httplib and LibreSSL are gone, with their submodules. libSceHttp and NP invitations send their requests with libretro-common's net_http, and HTTPS goes through libretro-common's own TLS 1.2/1.3 client. The PS4 redirect rules, the game's own headers and certificate-verification choices are kept. P2P packet encryption and signing use libretro-common's crypto: AES-128-CFB, HMAC-SHA1 and the platform's random bytes, with the same bytes on the wire. net_http's connection pool and DNS cache belong to one thread, so all of it now runs on a single network-service thread: callers hand it work through a lock-free ring, and a libSceHttp call waits on an eventcount for its own request, as the game asked it to. UPnP runs there too instead of on a thread of its own.
- LibAtrac9 is gone, along with the `externals/LibAtrac9` submodule. libSceAjm's ATRAC9 decoder now uses libretro-common's ratrac9, a clean-room decoder that gives bit-identical output and decodes about 2.8x as fast. A reset keeps the decoder's memory instead of freeing and allocating it again. Draining the rest of a superframe at the end of a track reuses the frame buffer instead of allocating one. A frame cut short no longer steps past the end of the input. The WAVE header's config is read with `ratrac9_parse_wave_fmt`.
- FFmpeg is gone, along with the `externals/ffmpeg-core` submodule. libSceAvPlayer, the last part that used it, now demuxes with libretro-common's rmp4, decodes video with rh264/rh265 and decodes AAC with raac. A host file is memory-mapped and its samples handed to the decoders in place. A file read through the game's callbacks or a backend handle is read into place as the demuxer reaches it: the header first, where it lies, even at the end of the file, then each sample in file order, every byte read once. Pictures are decoded straight into the game's frame buffers, and AAC into its audio buffers, with the encoder delay the edit list trims taken off the start. This also fixes the build: avplayer still called a video helper the videodec change had removed.
- libSceVdecsw is lock-free: the game's calls post to the decoding thread through a ring and take results and pictures from two more, with no mutex or condition variable left. The Sync calls wait on an eventcount, as the game asked to wait; the Try calls never wait. Access units are copied into buffers kept with the ring's slots, and pictures are decoded straight into the picture ring's buffers, so after warm-up nothing is allocated per access unit or picture. A reset starts a new epoch, and results from before it are dropped as they are read. `SetDecodeInput` returns `OUTPUT_PENDING` when the pictures not yet taken, plus the inputs in flight, would overrun the picture ring.
- The game's video decoders (libSceVideodec, libSceVideodec2 and libSceVdecsw) decode H.264 with libretro-common's rh264 and HEVC with rh265 in place of FFmpeg. Each picture is written as the console's NV12 frame in one pass from the decoder's planes, where FFmpeg's scaler first made an NV12 copy that was then copied again. A reset hands out and drops the pictures held for display order, and frees nothing. libSceVdecsw's queue of pictures decoded ahead reuses its buffers rather than allocating one per picture.
- The music player decodes AAC with libretro-common in place of FFmpeg: `.aac` (ADTS) with raac, `.m4a`/`.mp4` with rmp4 and raac, the track's edit list trimming the encoder delay. The decoded track is now one malloc'd buffer that rmp4's output is taken over into without a copy, and that MP3 and FLAC grow in place. The file extension is matched in any case.
- The game's MP3 decoder (libSceAjm's MP3) decodes with libretro-common's rmp3 in place of FFmpeg, frame by frame straight from the game's input, without a parser holding back data between jobs. Float and 32-bit output come from rmp3's float synthesis, 16-bit from its fixed-point one; FFmpeg's resampler is no longer involved. A frame whose bit reservoir reaches back before the stream was joined comes out as silence of the frame's length. Needs RetroArch's two rmp3 patches (float frame decode, a frame with part of the next behind it).
- miniupnpc is gone: the P2P port is forwarded through the router with libretro-common's `net/net_upnp.h`. Finding the router, mapping and unmapping now all happen on one thread of its own; callers only post the port they want forwarded and never wait for the router. The mapping is removed when the core shuts down. Needs RetroArch's net_upnp patch.
- The hwinfo library is gone: the CPU model and core counts in the log come from libretro-common's `features/features_cpu.h`. The total RAM and the operating system are no longer logged by the core; RetroArch's log has both.
- The Tracy profiler is gone: its hooks in the HLE libraries, the renderer and the GPU command processor, its Vulkan timestamp context and the library. Debug builds no longer open a profiler connection.
- fdk-aac is gone: the game's AAC decoder (libSceAjm's M4AAC) decodes with libretro-common's raac, AAC-LC, HE-AAC and HE-AAC v2 alike, from ADTS or raw streams. Each frame is decoded straight into the game's output buffer, in float when the game asks for float. 7.1 streams now come out as the eight channels the game asked for, where fdk-aac folded them down to 5.1, and without fdk-aac's output limiter, which reshaped and delayed the sound. HE-AAC frames now hand over all of their 2048 samples per channel; only the first 1024 were written before. Needs RetroArch's raac patches (ADTS header parse and WAVE channel order, parametric stereo).
- nlohmann::json is gone: nothing in the core uses it any more. The core no longer carries the library.
- The emulator settings (`config.json` and the per-game files in `custom_configs/`) and the users (`users.json`) are read and written in C89 with libretro-common's rjson, in place of nlohmann::json; the C++ classes and their per-call lock are gone. Members of those files this build doesn't know are kept when they are written, as before. Each file is written to a temporary file first and then renamed over the old one. A setting of the wrong type is now logged and left at its value, where a bad file stopped the core; a broken file is replaced with a good one. Strings are held in fixed buffers (256 octets, 4096 for paths), at most 16 game install directories and 16 users are kept. A `config.json` written now lists its keys in the order the core knows them rather than sorted.
- The HTTP host overrides (`host_overrides.json`), the patch repositories' `files.json` index and the body of a shadNet session invitation are read and written in C89 with libretro-common's rjson, in place of nlohmann::json. At most 64 host overrides are kept; more are logged and skipped.
- The key file (`keys.json`) is read and written in C89 with libretro-common's streaming JSON parser and writer (`formats/rjson.h`), in place of nlohmann::json. It is written to a temporary file first and then renamed over the old one, so a failed write no longer leaves it half-written. It is no longer written again when the core shuts down.
- stb_image and stb_image_write are gone: the overlay's PNGs (trophy icons and the like) decode with libretro-common's rpng. A PNG that fails to decode is now skipped instead of uploaded from a null image.
- CLI11 and ImGuiFileDialog are no longer built: nothing in the core used them.
- pugixml is replaced by libretro-common's rxml for the trophy files and the memory patches. A file is parsed in place from the buffer it is read into. Comments in a user's trophy progress file are not kept when it is written back.
- libpng and zlib-ng are gone: the game's PNG libraries (libScePngDec, libScePngEnc) decode and encode with libretro-common's rpng. A PNG decodes straight into the game's image buffer and encodes straight into its output buffer. An RGBA encode now honours the game's row pitch, which it ignored before. With this, the core carries no zlib at all.
- ZArchive and zstd are replaced by libretro-common: a game packed as a `.zar` is read with `formats/zar.h` from a memory mapping of the archive (`streams/file_stream.h`). Reads no longer pass through one shared worker thread under a lock: each thread reads on its own, and a file's octets go straight to where the game wants them. Paths inside an archive are now matched without regard to ASCII case. The AMD reciprocal tables decode with `encodings/rzstd.h`.
- The core's own inflating no longer uses zlib: PKG blocks and gzip HTTP bodies inflate with libretro-common's `encodings/deflate.h`. A gzip body is inflated into a buffer of the size its trailer records, made once. zlib-ng is left only for libpng, which the game's PNG libraries are built on.
- miniz is gone. The game-facing zlib library (`sceZlibInflate`) inflates with libretro-common's `encodings/deflate.h`. The pipeline cache is always kept as files in the game's cache folder: the zip-archived form (`pipeline_cache_archived`, off by default and not a core option) is gone with its setting.
- minimp3 and dr_flac are replaced by libretro-common's MP3 and FLAC decoders (`formats/rmp3.h`, `formats/rflac.h`) for the music player and the custom trophy sound. A track is decoded straight into the buffer it plays from, with no copy afterwards, and a track decoded with FFmpeg (AAC, M4A, MP4) is no longer copied once more after decoding.
- xxHash is replaced by libretro-common's XXH3 (`encodings/xxh3.h`), which gives the same hashes. Hashing a texture's backing memory no longer allocates.
- Discord Rich Presence is gone (it was off by default, and the core builds were made without it), with its `discord_rpc_enabled` setting and the discord-rpc library.
- SDL3 is gone from the core: no longer built, linked or carried. Building on Linux no longer needs the ALSA, PulseAudio, GLES, EGL or GL development packages.
- The emulator no longer makes a hidden SDL window, nor runs an SDL event loop: the core's input comes only from RetroArch's ports, and a mouse or keyboard a game asks for reads as not connected. Gone with it: the keyboard, mouse and gamepad bindings of standalone shadPS4 (its input configuration files and hotkeys), SDL's gamepads and their light bar, gyro and rumble (rumble goes through RetroArch, as before), the quit dialog, and the settings only those read (`cursor_state`, `cursor_hide_timeout`, `motion_controls_enabled`, `use_unified_input_config`, `default_controller_id`, `background_controller_input`, `use_mice_as_mice`, `use_keyboard_as_keyboard`). The one-time prompt to migrate saves and trophies from standalone shadPS4's old layout goes too. The overlay is now drawn at the size of the picture when Resolution is Default, not at the configured one.
- The microphone and the camera no longer open the system's own devices through SDL, past RetroArch. A game finds no microphone (it reads silence, at a microphone's pace) and no camera attached, which was already the camera's default. Both now take their input from a backend of their own, so RetroArch's microphone and camera can be plugged in later. The `sdl_mic_device` and `camera_id` settings are gone.
- The old configuration is no longer carried over: a `config.toml` from before the JSON settings is not offered for migration (that asked with an SDL message box, which a core cannot show) and its trophy key is not read, network keys under `General` and the `WindowsGuestRedZoneProtection` section are no longer read as their current names, and the audio keys for the removed backends (`audio_backend`, `openal_*`, `sdl_main_output_device`, `sdl_padSpk_output_device`) are gone; a `config.json` that has them loads and drops them when saved. The toml11 library goes with it.
- The trophy sound and the music player (a game's custom soundtrack) are played through RetroArch, in the core's mix, where each opened an audio device of the system's own past RetroArch, its volume, latency and recording. The trophy sound, built-in or the custom `trophy.mp3`/`trophy.wav` in the user folder, is decoded and resampled once when the game starts, so a trophy unlocked in play decodes nothing; the custom WAV file is read in place. Sound that is not the console's own 48 kHz is resampled with a 16-tap windowed sinc. The Volume option now applies to the music player as well.
- Sound no longer goes through SDL. Each audio port converts what the game writes to 16-bit stereo, with its volume, straight into an input of the core's own mix, which hands it to RetroArch; 16-bit stereo ports pass through unchanged, where SDL converted them to float and back. A port that waits for RetroArch to take sound is woken the moment it does, where it looked again every millisecond, and nothing is allocated while the game plays. The mix uses libretro-common's lock-free rings and eventcounts, now in the source under `libretro/libretro-common/`.
- The CMake option ENABLE_TESTS is gone: it could only stop the configure step, as upstream's tests are not in this repository.
- The standalone's big-picture launcher and in-game settings dialog, its window icons and its screenshots are gone from the source. None of them could be reached in the core, whose window is hidden and gets no keys: RetroArch takes screenshots, and the emulator's settings are core options. The core no longer makes an empty `screenshots` folder in `system/shadPS4/`, and no longer reads the game's icon at start to put on a window nobody sees.
- OpenAL is gone, and with it the emulator's audio backend setting: Audio3D always goes out through the frontend. With `audio_backend` set to OpenAL in the emulator's config file, a game's Audio3D sound went straight to the system's audio device, past RetroArch and its volume, latency and recording; it now comes through RetroArch like the rest of the sound. The core is smaller by the OpenAL Soft library it carried.
- The standalone's window presentation is gone from the source: the Vulkan surface, the real swapchain with its present modes and semaphores, and the HDR swapchain switch, none of which the core ever used. The game is told there is no HDR output, as it was before.
- The source builds the core and nothing else: the CMake option ENABLE_LIBRETRO and the LIBRETRO define are gone, along with the standalone's code paths they kept apart (its window, fullscreen and icon handling, its audio device and OpenAL backend selection, the swapchain on a window surface, its screenshots of the presented picture, its executable link settings). Nothing changes for someone using the core; a build no longer passes `-DENABLE_LIBRETRO=ON`.
- Linux and macOS: a crash on a thread that is not the game's (RetroArch's own, a driver's) is no longer the emulator's: it goes to the signal handler there was before the core's, so the system's crash report names it, where the core logged it as an unhandled signal and shut the emulator down. When the core takes its handlers out, the ones there were before come back instead of the defaults, so later crashes are reported again (sco8487).
- With PKG Content at Run from PKG, a game that asks for the size of a file it has open (fstat) gets it: since the last merge of upstream, the emulator answers fstat only for a file with an inode, and a file read out of a PKG had none, so the game got an error. Horizon Chase Turbo, a Unity game, stopped at start with an access violation right after opening its `global-metadata.dat`; it now reaches its menu as it does from an installed game.

The core's own handling of additional content (PKGs beside the game's, PKGs that cannot be read) is carried over to upstream's new loader.
- GPUs without sparse buffers at all (Intel HD Graphics 615 and other Intel Gen9 GPUs under Mesa) no longer lose the device on the game's first frame ("Device lost during submit"): the buffer cache's arenas there are plain buffers of 64 MiB, each backed whole by memory of its own from the moment the game first uses that part of its memory, where they were sparse buffers the device cannot make. That costs more memory than on other GPUs. Other devices are untouched. Tried on Linux x86_64 on an Intel HD Graphics 615 (Mesa 25.2.8): Sonic Mania Plus plays, where it lost the device on its first frame before, and Horizon Chase Turbo gets to a race; its picture stays black for the first minutes while its shaders are built the first time, with the music already playing.

With a software video filter on (scanline2x), the filter wrote past its buffer and took RetroArch down.

The option has a new key, so a Resolution set before is back to Default once.

## Test build 1 - 2026-10-11

The first build of the core. Based on upstream shadPS4 3a9f572. It has been built for Windows and Linux x86_64 and not yet run on real hardware by anyone: games may not start at all.

### The core

- The emulator builds as a libretro core, `shadps4_libretro`. Loading a dumped game's `eboot.bin` starts it.
- The core does not run the emulator inside the frontend's process. It starts itself again in a second process and trades with it through shared memory: the picture and the sound come out, the pads and the core options go in, the pads' motors come back. On Windows the second process is `rundll32.exe` loading the core; on Linux it is a small launcher carried inside the core and run from memory.
- Closing content ends that process and leaves the frontend running. Another game can be loaded afterwards.
- A game that crashes, or quits on its own, does not take the frontend with it: the frontend is told to close the content, and after a crash a message says so.
- The emulator's process ends with the frontend however the frontend ends.
- Everything the emulator writes (settings, logs, saves, shader cache) goes under the frontend's system directory, in `shadPS4/`.

### Picture, sound and pads

- The picture is shown by the frontend. The renderer draws into images of its own in place of a swapchain, and each finished frame is read back from the GPU and handed over as a software frame, so it does not depend on the frontend's video driver. The emulator's own window is still created, but hidden.
- The picture is the Output Resolution exactly, and that is also the largest picture the frontend is told to expect.
- The sound is played by the frontend. Each of the game's audio ports is converted to 16-bit stereo at 48 kHz and they are mixed; every frame the frontend gets one frame's worth, with silence for what is missing.
- Up to four controllers: the Controllers option says how many of the frontend's ports are connected to the console (one by default). Buttons, both sticks, analog triggers and rumble; Select is the touchpad button. SDL's own gamepad handling is off in the core, so a pad is not read twice.

### Core options

- Twenty-five options in five categories, set on top of the emulator's own configuration when a game starts, with the standalone's defaults. System: PS4 Pro Mode, Console Language, Devkit Console Mode, Additional Memory, Confirm Button, Connected to Network, Controllers, Show Splash Screen. Video: Output Resolution, FSR Upscaling, FSR Sharpening, FSR Sharpening Strength, VBlank Frequency, GPU Readbacks, Direct Memory Access, Readback Linear Images, Shader Cache, Show FPS Counter. Audio: Volume. Trophies: Trophy Notifications, their position and duration. Logging: Logging, Separate Log Files, Log Sync.
- The option texts can be translated through libretro's Crowdin project: `intl/` scripts, the upload and sync workflows, and `libretro_core_options_intl.h` (all English until the first sync).

### Repository and builds

- The repository holds the core only: upstream's standalone entry point, packaging files, tests, documents and contributor files are removed (`.upstream-excluded`), and the README describes the core.
- CI builds the core for Linux and Windows x86_64 (`.github/workflows/libretro.yml`), in place of upstream's workflow.
- A recipe for libretro's buildbot (`.gitlab-ci.yml`), Linux x64, and a GitHub workflow that replays it (`gitlab-preflight.yml`). The core info file is in libretro's full format.

### Known limits

- x86-64 only: the emulator runs the game's code directly on the host CPU.
- The picture is copied through system memory on its way to the frontend, which costs speed at high output resolutions.
- No save states: the emulator has none.
- Core options take effect when the next game is started, not while one runs. A setting without a core option is in the emulator's own config files under `system/shadPS4/`, and a per-game setting there wins over the core option.
